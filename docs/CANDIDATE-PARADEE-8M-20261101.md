# Candidate: Paradee-8M (text-to-speech), 2026-11-01

Requested by the repository owner on 2026-11-01: *"for TTS models we want to add as a candidate
Paradee-8M-v1.1"*. That is what this record is. **Nothing here is a measurement of Paradee**, and
nothing here is authorized beyond the candidate record itself — the sections below that read as
plans are recommendations, and they are labelled as such. The artifact facts are ours, read from
the bytes (`docs/model-evidence/paradee-8m/`); every quality and speed figure is the publisher's.

## Status, later on 2026-11-01

The owner decided **v1.2** the same day and asked for the qualification to run. What exists now,
and where:

- **Runtime (recommendation 1): built.** `models-backend-onnx` on branch `feat/paradee-8m-tts`
  of the models repository (PR integrallis/models#326): a pure-Java eager executor for the 56
  operators the int8 graph uses, kernels on the Vector API. **Seeded parity closed, 40 of 40
  cases** (fp32 and int8 graphs, four voices, five sentences each) against onnxruntime 1.23.2:
  PCM cosine 1.000000 throughout, worst signal-to-difference 63.37 dB against the 20 dB floor
  (`experiments/paradee-8m-tts/evidence/parity/seeded-parity-2026-11-01.json` there).
- **Phonemizer (recommendation 2): built, and its own number measured.** The Java misaki port
  resolves every word of the Harvard sentences but one (1 of 1,765 words, both accents) and
  drops **4.1 % of the words of the WikiText held-out set** (161 of 3,896 in US spelling, 160 in
  British; 90 and 91 of 200 sentences touched), which is the eSpeak fallback the port does not
  carry showing up as proper nouns (`experiments/paradee-8m-tts/evidence/phonemizer/`). The
  exact-match rate against the publisher's phonemes is derived once the arms finish. The four
  misaki dictionaries now ship inside `models-audio`, so a catalog entry needs only the
  publisher's two files.
- **Gate (recommendation 3): frozen and running.** The protocol is
  `experiments/paradee-8m-tts/README.md` in the models repository; the publisher's held-out
  200 WikiText sentences turned out to be published (`training/data/wikitext_sents.json`, first
  200), so the corpus is the publisher's own plus the Harvard sentences. The WER passes of both
  arms are running on the dev box; the throughput passes need a quiet machine and are recorded
  separately. **No verdict exists yet.**
- **This branch** carries, beside the record: `modeljars contribute` accepting an ONNX graph
  with its `config.json`; the cache path and the catalog's loadable-format check accepting
  `format: onnx` with a file list; the modality claim gate reading an ONNX graph's typed
  interface and the pinned config as its declared task, with the evidence record for this
  artifact; and the catalog entry `sahilmahendrakar_paradee_8m_v1_2_onnx_int8` **as a
  candidate**, with no `catalogPublishedAt` and no qualification. The speech loader's `paradee`
  branch waits for the models release that carries the runtime, per the bottom-up release

## Why it is worth carrying

It is the smallest credible TTS model there is: 7.9M parameters and 8.46 MB in int8, against
Soprano's 80M and 117.5 MB. Smallest-first is the catalog's founding rule. It is a distillation of
Kokoro-82M, the TTS candidate already on the roadmap, so if it holds up it reaches the Kokoro place
at a tenth the size — one voice at the pinned v1.1, or two American and two British at v1.2 if that
recommendation is taken. Apache-2.0 throughout, first-party code the author runs themselves, and a
named judge for its published quality figure.

## The intake CLI refuses it, which is the clearest statement of the format blocker

`modeljars contribute` is the established way to record a candidate — it writes
`docs/onboarding/<slug>/candidate.md` with a `modeljars-candidate-v1` marker. Run against Paradee
with every published file selected, it refuses:

```
modeljars contribute sahilmahendrakar/Paradee-8M-v1.1 \
  --revision 330617ad1f097b4f6b02c103e54b39006c090b45 --license Apache-2.0 \
  --capability text-to-speech --domain general \
  --file onnx/paradee_int8.onnx --file onnx/paradee.onnx \
  --file pytorch/text_side.pt --file pytorch/decoder.pt \
  --file config.json --file tokenizer.json

Error: Selected files do not contain GGUF, CACT, or Safetensors model weights
```

`HuggingFaceContributionService.detectFormat`
(`modeljars-cli/src/main/java/org/modeljars/cli/HuggingFaceContributionService.java:333-343`)
accepts `.gguf`, `.cact` and `.safetensors` and nothing else. So this document is the candidate
record, because the tool that would normally produce one cannot.

## What the triage found

Both versions were triaged: `docs/model-evidence/paradee-8m/TRIAGE-v1.1.md` (the pin) and
`TRIAGE-v1.2.md`. Figures below are **v1.1 / v1.2** where they differ.

- **No GGUF and no safetensors**, in either version. ONNX fp32, ONNX int8, and two PyTorch halves.
  The catalog loader reads neither ONNX nor `.pt`, so this is a new loader as well as a new
  architecture.
- `model_type` is `paradee`; 24 kHz output; `n_token` 178, an IPA phoneme vocabulary inherited from
  Kokoro, 114 symbols in `vocab`. Soprano is 32 kHz.
- Inputs `input_ids` int64 `[1, tokens]` and `speed` float32 `[1]`, plus **`voice` int64 `[1]`** at
  v1.2 — the only graph change between them, each half having gained a four-row table indexed by
  voice.
- Initializer elements in the int8 graph: **7,867,115 / 7,867,227**, which confirms the card's
  7.88M from the bytes in both. The 112-element difference is those voice tables.
- The same four operator families appear in both graphs and **nowhere in `models-audio` or
  `backend-java`**: `InstanceNormalization` (22), `ConvTranspose` (7), `LSTM` (6), `Resize` (3).
  The LSTMs come from Kokoro's text side, which the author says is "Kokoro's own code at smaller
  widths".
- `RandomNormalLike` (1) in both: the graph draws its own noise.
- **2,113 / 2,117** nodes over 53 operator types in fp32; **2,529 / 2,535** over 56 in int8, the
  extra being `DequantizeLinear` (105) and casts.

## What qualifying it would require — three recommendations, none of them authorized

Each of the three blockers is a decision rather than a measurement, so each is written out with
the option taken and the reason. **These are proposals.** Nothing below has been approved, started,
or costed with the owner, and the work in each is weeks rather than days.

### Recommendation 1 — runtime: a pure-Java ONNX executor in `models-backend-onnx`, not a conversion and not onnxruntime

The catalog pins the publisher's artifact by revision and digest. A GGUF or safetensors conversion
we author is an artifact that provenance model does not describe, and it would make the thing
qualified something the publisher never shipped. The alternative, binding onnxruntime through its
Java API, is permissively licensed (MIT) but is a native C++ engine, which is not what this runtime
is: the decoders here are Java on the Panama Vector API with Rust shims we wrote. So the decision
is an **eager, opset-17 ONNX executor in `models-backend-onnx`**, the module that has been reserved
for exactly this and holds one `package-info.java`, covering the 56 operator types this graph
uses, with `Conv`, `MatMul`/`Gemm`, `LSTM`, `ConvTranspose`, `InstanceNormalization`,
`LayerNormalization`, `Resize` and `DequantizeLinear` as the kernels that carry the cost. The
int8 graph is the catalog artifact (it is the one the publisher says to use); the fp32 graph is
the parity reference for the executor. The catalog `format` becomes `onnx`, which means
`HuggingFaceContributionService.detectFormat` (`modeljars-cli/.../HuggingFaceContributionService.java:333`)
accepts `.onnx` beside `.gguf`, `.cact` and `.safetensors`, and the modality claim gate, which
today reports every non-GGUF entry as `UNVERIFIABLE` with "this gate reads GGUF headers"
(`tools/modality-claim-gate.mjs:120-124`), gains an
ONNX evidence record read from the graph's inputs and outputs and the pinned `config.json`
(`model_type`, `sample_rate`, `voices`), the declared-task analogue of soprano's
`audiocpp.model_spec.json`.

### Recommendation 2 — grapheme-to-phoneme: a Java port of misaki's English lexicon path, measured against misaki

The graph takes misaki-spelled IPA and this tree has no phonemizer. The publisher's own pipeline is
`misaki.en.G2P(trf=False, british=…, fallback=espeak.EspeakFallback(british), unk="")`
(`paradee/tts.py` @ `aae3cc46`). misaki's English path is a lexicon (`us_gold`, `us_silver`,
`gb_gold`, `gb_silver`, 12.6 MB of JSON, Apache-2.0, pinned at `fba1236`), -s/-ed/-ing stem rules,
number and currency expansion, stress rules, and part-of-speech special cases that need spaCy; the
fallback for words the lexicon lacks is eSpeak NG, GPL-3.0.

The port carries the lexicons, the stems, the numbers and the stress rules, and the sentence split
the publisher uses. It does **not** carry eSpeak (license) or spaCy, so two things degrade and both
are measured rather than assumed: out-of-vocabulary words are dropped exactly as the publisher's
`unk=""` drops them when its fallback fails, and heteronyms that misaki resolves by part of speech
may resolve differently. **The phonemizer gets its own number**: per-sentence exact-match rate of
our phoneme string against the publisher's pipeline on the qualification corpus, with the
out-of-vocabulary rate reported beside it. The TTS gate then runs twice, once on the publisher's
phonemes (which isolates the graph port) and once on ours (which is what a user gets); both are
published.

### Recommendation 3 — gate: the shipped performance block, round-trip WER in place of the oracle block, seeded parity on the side

`speech-oracle-streaming-latency-v1` qualified both Soprano entries on PCM cosine against the
publisher's own PyTorch implementation (0.998389 and 0.999331; 24.9 dB and 28.7 dB) plus streaming
behaviour and p95 real-time factor and time-to-first-audio over five trials. The oracle half of
that gate is undefined for a model that draws its own noise: there is no single reference waveform.

The models repository corrected its harness design on 2026-11-01 after reproducing the shipped gate
on Soprano (`models-q8f32-kernel/docs/QUALIFYING-MODELS-OUR-HARNESS-CANNOT-MEASURE.md` §3,
`benchmark-results/2026-11-01-soprano-tts-gate-reproduction/`): the separately designed
`production-tts-synthesis-v1` policy is **withdrawn**, because a TTS gate already ships, and
round-trip WER is kept **for the nondeterministic-vocoder case only**, with the existing
performance block reused unchanged. Paradee is that case, and this is the decision:

| gate | rule | status of the number |
| --- | --- | --- |
| intelligibility (replaces the oracle block) | **round-trip WER**: synthesize a pinned sentence set, transcribe with a pinned ASR judge, score against the input text, per voice. The judge is Whisper base, because that is the publisher's judge, pinned by package version and model digest, with the Open ASR Leaderboard text normalizer pinned by version. Floor: our WER per voice within the comparator arm's replication spread of the comparator's WER on the same sentences and the same judge | floor is relative to our own comparator run, never to the card's 5.8% |
| performance (unchanged) | the shipped block: **p95 real-time factor and p95 time-to-first-audio over five trials**, and additionally the **RTF ratio ≥ 0.80** against onnxruntime on the publisher's own package, same host, same thread count (1 and the host's physical cores), same sentences. First audio arrives after the first sentence, because the publisher's pipeline and ours synthesize sentence by sentence; the entry records that the graph itself is not streaming | thresholds inherited; the Soprano reproduction measured a **2.68x** p95 RTF spread between two passes of one artifact on this machine, so one pass carries no verdict and warm-up is recorded |
| port correctness (beside the gate, not the verdict) | **seeded parity**: `RandomNormalLike` is externalised into a graph input by a recorded script on both arms (same weights, same operators, only the noise source moved), then PCM cosine ≥ 0.995 and signal-to-difference ≥ 20 dB per the shipped policy, per voice. This proves the executor; it is not the qualification verdict, because it compares against a graph the publisher does not ship | thresholds inherited from `speech-oracle-streaming-latency-v1` |
| replication | three passes; the **minimum across passes** clears each floor | the Soprano reproduction is the reason |

Proposed policy id for the record: `speech-roundtrip-wer-streaming-latency-v1`, a sibling of the
shipped policy that differs in the quality block only. The name is a proposal until the models
repository's harness carries it.

What it refuses to claim: round-trip WER is intelligibility. UTMOS is a learned naturalness
predictor and Kokoro's standing is a human Elo; neither is reproduced here and the entry says so.

**Corpus.** The publisher's 200 held-out WikiText-103 sentences are unpublished, so the corpus is
ours and frozen before any run: a pinned, seeded draw of WikiText-103 sentences (the publisher's
distribution) and the Harvard sentences (public domain) as the second dataset, per the
two-dataset rule. Sentence lists, seeds, judge versions and thresholds go into
`experiments/paradee-8m-tts/README.md` in the models repository before the first arm runs.

**Validate the judge on Soprano first.** The shipped gate's performance half has been reproduced on
Soprano; the round-trip judge has not. Running Whisper base over Soprano output, whose waveform
parity is already proven, is the cheap check that the judge pipeline scores a known-good model
before it scores a new one.

## Proposed order of work, if the recommendations are accepted

Not started. Step 0 is the owner's decision on whether to do any of it at all, and on v1.1 against
v1.2.

1. Freeze `experiments/paradee-8m-tts/README.md` in the models repository: corpus, seeds, judge,
   thresholds, kill criterion.
2. Comparator arm alone, publisher's package pinned (`paradee` @ `aae3cc46`, onnxruntime pinned),
   on the dev box: per-voice WER and RTF, three passes, which fixes the floors. Judge validated on
   Soprano the same day.
3. ONNX executor: parity against onnxruntime per operator on dumped intermediates, then seeded
   whole-graph parity on the fp32 graph, then the int8 graph.
4. misaki port: phoneme exact-match rate against the publisher's pipeline on the corpus.
5. Candidate arm through `TextToSpeechModel`, two-arm run, verdict per voice, performance block
   derived by script (the Soprano reproduction's `derive.py` is the precedent; nothing hand-typed).
6. Catalog entry (`format: onnx`, four voices, sentence-level streaming recorded as such),
   `contribute` and the modality gate extended, smoke record, release gates per the campaign runbook.

Steps 1 to 5 would be models-repository work on their own branch there; this branch carries only
the candidate record, the evidence, and the roadmap entry. No catalog data file is touched, because
nothing is qualified.

## Not done, and not claimed

No port exists. No Paradee audio has been synthesized here, by our runtime or by onnxruntime. No
owner decision has been taken on the three recommendations or on v1.1 against v1.2. The
publisher's 62.1x, 4.40 and 5.8% have not been re-derived and must not be published as ours. The
publisher's three speed figures for this family (62.1x on the v1.1 card, 25.0x in the paper, 18x in
the repository description) disagree by 3.4x because each was taken in a different setup.
