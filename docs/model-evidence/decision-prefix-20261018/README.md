# Where a decision's resumption point belongs

Harriet composite, Qwen3.5-4B Q4_K_M, pure-Java backend. The quoted figures were measured
2026-10-19 on an isolated Hetzner `ccx33` (8 dedicated vCPU AMD EPYC-Milan, AVX2, no AVX-512)
provisioned for this experiment and deleted after it; the workstation runs (i9-14900HX, AVX2, no
AVX-512) are retained beside them and are not comparable between themselves. Both hosts run the
same kernels: AVX2, no AVX-512.

## What was wrong

`ModelJarDecisionRuntime` held one resumption point, captured after the shared prefix. The shared
prefix is `state + "\n" + criteria` -- the evidence **and the rubric** -- so the point was reused
only by a question whose rubric was byte-identical. A batch of unlike questions (a boolean, a
choice over queues, an ordered severity: the shape `decideAll` is documented for) matched nothing,
and every question in it re-read the evidence.

`decideAll`'s javadoc said "the cost of the evidence is paid once rather than once per question".
That was true only for same-rubric batches. The condition was stated in an internal comment on the
grouped path and nowhere a caller would read it.

## What a second point would have cost

The first fix kept two points -- one after the evidence, one after the whole prefix -- and worked:
`two-point-candidate.log`. Then the retained state was measured rather than assumed.
`snapshot-cost.java` prefills a ticket, takes ten captures in turn and reads the live heap after a
collection between each:

```
CAPTURES    LIVE HEAP MIB PER CAPTURE KIB
0                   724.6              -
1                   822.9       100610.7
5                  1216.0       100628.0
10                 1707.4       100634.0
```

**98.3 MiB per capture, flat in prefix length.** A second point is a second copy of the model's
linear state on every open decision runtime, which is not a reasonable price for a latency win.

## The change

One point, whose level is chosen by what is being asked.

- `decideAll` sees every question before it answers any of them, so it decides: one rubric across
  the batch means capture after the whole prefix, and every question after the first reads only its
  own criterion. Rubrics that differ cannot share a prefix however it is captured, so the point goes
  after the evidence and each question re-reads only its own rubric.
- `decide`, asked one question at a time, cannot be asked to know its own future. It starts where a
  single question is cheapest and moves once a second rubric over the same evidence proves the
  questions are unlike -- one extra read of the evidence, once, instead of one per question.
- A tokeniser that does not split the evidence from the rubric on the same boundary as the whole
  prefix makes the split unsafe, so it is checked the way the grouped path already checks its own,
  and falls back to reading the prefix whole.
- Both the point and its level are dropped on any reset, because a capture is resumable only while
  the session's token history still begins with the tokens it was taken after.

The tokens the backend ends up having read, and the positions they sit at, are unchanged. The
prompt is unchanged and the answer is unchanged.

## Protocol

`grouping.java` asks one, two and three questions about one 250-token ticket in three shapes -- one
shared rubric, three different rubrics, and no rubric at all -- after a discarded warm-up batch,
with a unique marker sentence per batch so no batch resumes a previous batch's evidence. It prints
every verdict's probability and confidence to six places, which is how the answers are compared,
and the live heap after a collection, which is how the capture count is checked from outside.

**The numbers quoted anywhere come from an isolated host.** The workstation runs the user's editor
and screen recorder: two runs of this probe on identical code differed by 1.14x there, and one pair
by 2x on paths the change cannot touch. So both builds were run twice each on a Hetzner `ccx33` --
8 dedicated vCPU AMD EPYC-Milan, 30 GiB, Ubuntu 24.04, load 0.00 at first contact -- provisioned
for this measurement and deleted after it. `vps/PREFLIGHT.md` holds the shape, the live price, the
host key, the ceiling and the closing audit; `vps/host-baseline.txt` holds the machine.

Builds compared: the released 0.1.61 artifact resolved from Central, and the candidate published to
the local Maven repository as 0.1.62, copied to the host as three artifacts with their SHA-256
compared on both sides, and deleted locally afterwards.

## Result

[COMPARISON.md](COMPARISON.md), generated by `compare.py` from the logs beside it.

On the isolated host, three questions with three rubrics:

| | 0.1.61 | 0.1.62 candidate |
| --- | --- | --- |
| three unlike questions | 16,497 and 16,618 ms | 7,766 and 8,300 ms |
| each question after the first | 5,539 and 5,584 ms | 1,378 and 1,466 ms |
| the same, as a multiple of one question | 3.04x and 3.05x | 1.55x and 1.55x |

**2.00x to 2.12x** on the batch shape `decideAll` is documented for, and the question after the
first costs **3.8x to 4.0x less**. What it cost before was a second reading of the whole ticket;
what it costs now is a reading of its own rubric, which is the irreducible part.

Nothing else moves:

- **a same-rubric batch is unchanged**: 6,343 and 6,416 ms against 5,895 and 6,276 ms for three
  questions, inside the spread between two runs of the same build
- **no-rubric questions are unchanged**: 5,638 and 5,679 ms against 5,180 and 5,527 ms
- **live heap is 822 MiB after a collection in all four runs**: one resumption point, not two
- **all 15 measured verdicts are identical** across both builds and both passes. The sixteenth
  answer, in the batch the probe discards, moves by up to 0.012 -- between two runs of the same
  build as much as between builds, because it is the process's first forward pass
- on the workstation, where the backend is bit-identical run to run, all four runs of both builds
  agree to six places on every answer including the warm-up

## What this does not show

- **One machine, one model, one evidence length.** The saving is the evidence read, so it scales
  with evidence length; a short ticket saves less. A 250-token ticket is what a support queue
  looks like, not an upper bound.
- **Nothing about concurrency.** One runtime, one session, one thread of calls.
- **The `decide`-at-a-time path pays once to learn.** A caller alternating rubrics through
  `decide` re-reads the evidence on the question that changes rubric, and not after that. A caller
  alternating between two evidence strings *and* two rubrics defeats a single point entirely; that
  case is not measured and is not claimed.
- **The grouped path is unchanged.** Grouping is off by default on this backend because its answers
  are not bit-identical, which is a separate and already-documented decision.
- **The 98.3 MiB per capture was measured on the workstation**, where the probe could hold ten
  captures at once. It is a property of the model's linear state, and the isolated host's flat
  822 MiB across both builds is consistent with it, but the per-capture figure itself was not
  re-measured there.
