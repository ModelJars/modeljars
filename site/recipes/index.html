Compositions

Recipes

A hybrid is a catalog category, not one construction. Every composition in the catalog is assembled by a named recipe, and recipes need not share architecture with one another: one forks a specialist from a base's KV cache, one reads a decision off a frozen base in a single pass, one votes between independent models token by token. The card and the detail page of every composition name its recipe; this page says what each recipe is, what it shares and what it does not, how it opens from Java, and what qualifies it.

Shared-prefix activated LoRA

Category: hybrid · recipe id shared-prefix-activated-lora

One base model and one activated low-rank adapter trained for a specialist job. The base handles ordinary chat. When the specialist is invoked, its branch forks from the same physical KV-cache prefix the chat already computed, applies the adapter's low-rank delta from the activation point on, and answers; the base's state is untouched. The adapter is a composition component, not a second standalone model, so the second behaviour costs no second set of weights in memory and no second prefill of the conversation.

What is shared

  • The base weights, loaded once.
  • The KV-cache prefix up to the activation point, by physical block identity (the catalog lists this as exact-kv-block-sharing and shared-physical-prefix).

What is not

  • The adapter's own delta and the specialist branch's tail of KV state, which diverge from the activation point on.

How it opens

try (var hybrid = ModelJars.openActivatedToolRuntime(BASE.MODEL, ADAPTER.MODEL);
     var conversation = hybrid.openConversation()) {
  var prompt = hybrid.chatTemplate().render(List.of(ChatMessage.user("...")));
  var answer = conversation.generateBase(prompt, options);   // ordinary chat on the base
  // the specialist verdict forks from the same prefix; see the composition's page
}

What qualifies it

The base is qualified on its own. The adapter is a hidden component bound by the composition's evidence: a controlled comparison of the complete recipe against its control on a frozen window of published cases, with the composite's median latency recorded beside the control's. The detail page shows that evidence under Composition evidence.

In the catalog: Granite 4.1 3B answerability hybrid.

Option-logit readout

Category: recipe · recipe id option-logit-readout

A frozen base model and a readout, no training and no generation. The question and its declared options are rendered once; the model runs one forward pass; the answer is read off the logits of the option letters and turned into a calibrated probability by a frozen temperature table. However many options there are, it is still one pass, and the result is a typed value (a proposition's probability, one of N labels, or an ordinal score) rather than text to parse.

What is shared

  • Nothing between models: there is only one. Several questions over one input can share that input's KV prefix where the base family supports it, which the catalog lists as shared-physical-prefix.

What is not

  • The base is not modified (frozen-base); the recipe stands on the base's own published qualification plus the readout's measured accuracy against its chance floor.

How it opens

try (var decisions = ModelJars.openDecisionRuntime(MODEL)) {
  var verdict = decisions.decide(question, options);   // typed, calibrated; no decoding loop
}

What qualifies it

Accuracy on a published decision cohort reported against the cohort's chance floor, with the calibration table frozen before the test window. The detail page shows it under Production evidence.

In the catalog: Harriet (Qwen3.5 4B decisions).

Entropy-gated logit fusion

Category: hybrid · recipe id entropy-gated-logit-fusion · status: runtime built, no catalog entry yet

Several independent models that share one tokenizer, byte for byte. One is the lead and always decodes. At every step the Shannon entropy of the lead's next-token distribution is read; while it is below a threshold the lead emits alone and the auxiliaries sit idle. When it reaches the threshold, each auxiliary catches up over the tokens it has not seen in one batched prefill call and the members' log-probabilities are combined as a weighted product of experts; the next token is sampled from that. The published recipe fuses a coding specialist (lead), a maths specialist and a general model of the same family at a threshold of 0.65 nats.

What is shared

  • The tokenizer, which must be identical across members (this is checked before anything loads).
  • The decoded token sequence: every member sees the same prefix, each in its own cache.

What is not

  • Weights and KV caches. Members stay separate models in memory; nothing is merged, so each keeps the sharpness weight-merging would blur. This recipe shares no structure with the shared-prefix activated LoRA recipe above; both are hybrids because both are assembled from more than one set of weights into one behaviour.

Why the gate

Fusing at every token was measured in September 2026 and lost to the best single member on a GSM8K pilot; published work (SAFE, ICLR 2026) reports the same and recovers the gain by choosing the positions, ensembling at a small fraction of tokens. The gate is that choice, and it is also what keeps the cost close to the lead alone: the auxiliaries only pay for the steps where they are asked.

How it opens

// Models runtime, com.integrallis.models.runtime.fusion
var recipe = new FusionRecipe(FusionRule.POE, new double[] {0.55, 0.25, 0.20}, new EntropyGate(0.65));
try (var fused = new FusedInferenceBackend(List.of(lead, maths, general), recipe);
     var pipeline = new InferencePipeline(fused)) {
  // generate as with any backend; fused.metrics() reports how often the auxiliaries voted
}

A catalog composition of this recipe will open through ModelJars like any other, with the members, weights and threshold taken from the catalog so that what ships is what was measured.

What qualifies it

A pre-registered study in the Models repository (benchmark-results/2026-11-25-gated-logit-fusion/PREREGISTRATION.md): the fused output must beat its best member and every-token fusion on at least two of three published datasets, cost at most 1.3× the lead alone, and stay within two points of a larger model at matched memory. The catalog carries an entry for the published recipe only if that practical claim holds. Until then this recipe is documented here and available as a runtime in Models, not as a catalog composition.

How recipes are named and checked

A recipe id names the architecture of the assembly, not the models in it. The catalog (catalog/compositions.json) names a recipe on every composition, the build refuses a name that is not on this page's list, and the card and detail page render the name with a link here. Adding a recipe means adding it to that list, explaining it on this page, and publishing its first composition only with the evidence its section describes.
